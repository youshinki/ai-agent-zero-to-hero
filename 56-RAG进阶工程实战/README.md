# 第56篇：RAG进阶工程实战 | 混合检索、召回偏差与检索重排难点
前面第9到18篇，我们把RAG从文档解析、切片、向量入库一路搭通，跑出了一个能问答的Demo。但真正把这套东西交付给企业客户，反馈几乎是同一句话：**"有时候答得挺准，有时候又完全驴唇不对马嘴。"**

你回去查日志会发现：切片没问题、向量库没问题、Prompt也没问题——**问题全出在召回这一层**。用户问"试用期离职要不要赔培训违约金"，向量库Top5里根本没有这条制度，模型只能瞎编；或者Top5里明明有，但排在第4位，被上下文窗口截掉了。

这一篇不重复基础原理，专门讲RAG工程化里三个最硬的骨头：**为什么要做混合检索、召回偏差到底偏在哪、重排序为什么是商用RAG的分水岭**。文末附面试高频问答。

# 一、纯向量检索的三种失效模式

很多新手做RAG，思路就是"把文档切片→embedding→存ChromaDB→query向量化→余弦相似度取TopK"。这套流程在演示Demo上百发百中，一上生产就露馅。原因是**向量检索本质上是"语义相似"，不是"信息查找"**，它有三个天生短板。

## 1. 专有名词、编号、精确术语召回不出来

企业文档里充满这种东西：合同编号"HT-2024-0815"、产品型号"XJ-3000Pro"、内部制度文号。用户直接搜这个编号，embedding模型会把它编码成一个"大概像编号"的向量，但库里那条原文的向量和它相似度可能并不高——**因为embedding模型对数字、编号几乎不敏感**，它把"HT-2024-0815"和"HT-2023-0902"编码得差不多。

## 2. 语义漂移：意思对了，内容错了

用户问"年假能攒到下一年吗"，向量检索会把"病假管理办法""加班调休规定"都召回，因为它们语义上都属于"请假"这个大类。**向量召回是"宽进"，它擅长找相关主题，不擅长定位到那一句精确答案**。

## 3. 位置偏差：正确答案排不到前面

这是最隐蔽的一个。我们后面专门讲重排序时会展开——bi-encoder双塔结构本身决定了，它打分是"粗排"，相关文档能进TopK就算成功，但谁排第一，它其实判断得很糙。

# 二、混合检索：BM25 + 向量，用RRF融合

解决方案不是二选一，而是**两条腿走路：BM25负责精确匹配，向量负责语义匹配**，最后用一个融合算法把两路结果合并。

## 1. 两路检索各自补对方的短板

| 维度 | BM25（关键词） | 向量检索（语义） |
|-|-|-|
| **擅长** | 编号、术语、产品型号、专有名词精确命中 | 口语化提问、同义改写、模糊表述 |
| **短板** | 用户换个说法就匹配不到 | 数字、编号、精确词条容易漂移 |
| **打分方式** | 词频 + 逆文档频率，稀疏 | 余弦相似度，稠密 |

## 2. RRF融合：别自己发明加权

两路各取TopK（比如各取20条），合并去重后需要重新排序。常见的错误做法是"BM25分数×0.4 + 向量分数×0.6"——**这两个分数根本不在一个量纲上，没法直接加权**。工业界标准做法是RRF（Reciprocal Rank Fusion），只看排名不看原始分数：

```python
def rrf_fuse(bm25_hits, vec_hits, k=60, top_n=10):
    """
    bm25_hits: [(doc_id, score), ...] 已按分数降序
    vec_hits:  [(doc_id, score), ...] 已按分数降序
    k: RRF 平滑常数，论文默认 60
    """
    scores = {}
    for rank, (doc_id, _) in enumerate(bm25_hits):
        scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank + 1)
    for rank, (doc_id, _) in enumerate(vec_hits):
        scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank + 1)
    ranked = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return ranked[:top_n]
```

RRF的好处是：**不管两路原始分数怎么分布，只要某条文档在两路里排名都靠前，它的融合分就高**。在两路里都被召回的文档，可信度天然更高——这正好解决了"单路检索漏召回"的问题。

# 三、召回偏差：TopK不是越大越好

做混合检索时，新手最爱犯的错就是"既然怕漏，那TopK设大一点，设50条一起塞给大模型"。这是个非常典型的工程误区。

## 1. TopK过大反而拉低答案质量

原因有三层：

- **上下文窗口被稀释**：塞进去40条无关片段，大模型注意力被分散，真正相关的那条被淹没。
- **引入噪声 = 引入幻觉**：检索回来的片段里有冲突信息时，模型更容易信那个"写得更像答案"的，而不是"写得最准的"。
- **成本线性上涨**：每多塞10条片段，输入Token就多几千，API账单直接上去。

工程经验值：**混合检索每路各取20\~30条，融合后保留Top20，再交给重排序精排到Top3\~5**。这个数字要拿真实业务问题集反复调，不是拍脑袋。

## 2. 分块粒度与召回率是耦合的

召回偏不准，很多时候病根在切片（第12篇讲过）。这里补充一个工程视角：**块切太大，一条里塞了好几个主题，向量被平均掉，语义不聚焦；块切太小，上下文不完整，召回回来孤零零一句话，模型没法作答**。商用项目里我通常的做法是主块500\~800 token，同时存一份200 token的小块做召回，命中后再把相邻大块取出来——这叫"小块召回、大块喂答案"。

# 四、检索重排：商用RAG的真正分水岭

这是面试里最容易拉开差距的一题。为什么bi-encoder双塔检索完了，还要再加一层rerank？

## 1. 双塔粗排 vs 交叉编码器精排

向量检索用的bi-encoder，是把query和document**分别**编码成两个向量再算余弦——为了快（可以预计算文档向量、建索引）。代价是query和document之间没有任何交互，"这句答案到底对不对"它其实没真看。

Cross-encoder重排序模型，是把query和document**拼在一起**送进同一个Transformer，让注意力机制充分交互后打分。精度高得多，但没法预计算，所以只能对已经粗排过的20\~30条候选做精排。

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank(query, candidates, top_k=4):
    # candidates: [(doc_id, text, fused_score), ...]
    pairs = [(query, text) for _, text, _ in candidates]
    scores = reranker.predict(pairs)   # 0~1 相关度
    ranked = sorted(
        zip(candidates, scores),
        key=lambda x: x[1], reverse=True
    )
    return ranked[:top_k]   # 精排后只取 3~4 条喂给大模型
```

## 2. 工程上三个必须知道的细节

- **rerank是延迟大头**：Cross-encoder推理比embedding慢一个量级，所以候选集必须控制在20\~30条以内，不能拿几百条去排。
- **阈值兜底比纯TopK更稳**：重排后设一个相关度阈值（比如0.3），低于阈值的片段干脆不喂给模型，直接走"知识库暂无相关内容"的兜底话术——**这是商用系统防幻觉的关键一环**。
- **rerank和混合检索不是替代关系**：很多人以为上了rerank就不用BM25了，错。rerank只能对"已经被召回的候选"重排，召回阶段漏掉的文档，rerank再强也救不回来。

# 五、工程踩坑清单

- **embedding模型和rerank模型不配套**：用英文embedding模型去索引中文文档，召回率天然打折。中文场景优先选bge系列这类原生双语模型。
- **召回结果不带元数据过滤**：企业多产品线共用一个知识库时，必须在检索前按"产品线/部门/密级"做元数据过滤，否则A部门的问题会召回B部门的文档。
- **不做召回评测就上线**：上线前准备50\~100条真实高频问题，每条标注"正确答案在哪个文档"，测Hit@5和MRR。没有这个基线，后面调参全靠玄学。

# 📝 面试高频问答

## Q1：为什么RAG要做混合检索？只用向量检索不行吗？

答：向量检索擅长语义匹配，但对专有名词、编号、精确术语不敏感；BM25正好补这个短板。两路并行召回，再用RRF按排名融合，能同时覆盖"口语化提问"和"精确词条查询"两类场景，召回率比单路提升明显。关键是两路分数量纲不同不能直接加权，要用RRF这种只看排名的融合方法。

## Q2：检索TopK设越大越好吗？

答：不是。TopK过大反而降低答案质量——噪声片段稀释大模型注意力、引入冲突信息诱发幻觉，还线性推高Token成本。正确做法是粗排阶段每路取20\~30条，融合后交给Cross-encoder精排，最后只保留Top3\~5条，并设相关度阈值兜底。

## Q3：bi-encoder和cross-encoder区别？为什么要两级？

答：bi-encoder把query和文档分别编码，可预计算、可建索引，适合大规模粗排，但两者没有交互、精度有限；cross-encoder把query和文档拼一起做全注意力交互，精度高但无法预计算、延迟大，只适合对少量候选精排。所以工业级RAG一定是"向量/BM25粗排召回→cross-encoder精排"的两级结构。

## Q4：RAG召回不准，你怎么定位问题？

答：分层排查。先看正确答案到底有没有被召回（Hit@5）——没召回是切片或embedding/召回策略问题；召回了但排在后面，是粗排排序问题，加rerank；精排后喂给模型还是答错，那就是Prompt、上下文组织或模型本身的问题，不是检索层的锅。

## Q5：怎么评估一个RAG系统的好坏？

答：拆成召回和生成两层指标。召回层看Hit@k、MRR、召回覆盖率；生成层看答案正确率、忠实度（有没有引用知识库外内容，即幻觉率）、引用可溯源率。线上还要监控用户"追问/差评"率作为业务侧信号。
